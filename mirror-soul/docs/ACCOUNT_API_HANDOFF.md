# 계정 관리 UX 및 백엔드 요청

## 이번 RN 변경

- `codex/profile-api-reliability`의 기존 작업을 이어 진행했다. 백엔드·AI·인프라 코드와 submodule 포인터는 수정하지 않았다.
- 화면을 내 계정 정보 / 화면 스타일 / 로그인과 도움말 / 회원 탈퇴로 구분했다. 라이트·다크 테마의 텍스트 색과 카드 스타일을 사용한다.
- 닉네임은 기존 `GET /my-page/account`, 로그인 이메일은 기존 `GET /my-page`로 조회한다. 이메일은 읽기 전용이며 이름·이메일 조회 실패는 각각 다시 시도할 수 있다. 서버가 제공하지 않은 인증 완료/소셜 연동/최근 로그인 상태를 추측해서 표시하지 않는다.
- 공개 프로필 미리보기와 기존 고객센터를 연결했다. 로그인 화면의 비밀번호 찾기를 안내하되, 로그인 중에 인증 전용 경로로 이동하거나 사용자를 임의로 로그아웃시키지 않는다.
- 테마 선택은 기존 로컬 저장소를 사용한다. 선택 상태를 색상·체크·스크린 리더 상태로 전달하며 좁은 화면과 큰 글자에서는 자연스럽게 줄바꿈한다.
- 닉네임 편집은 2~10자 한글·영문·숫자 규칙을 유지한다. 변경 전/잘못된 입력은 저장을 막고, 저장 실패 후에는 입력을 유지해 수정 없이 재시도할 수 있다. 조회가 갱신되어도 작성 중인 내용을 덮어쓰지 않는다. 저장 중 중복 요청과 닫기를 막고, 이전 계정에서 열린 폼은 다른 계정에 저장하지 않는다.
- 로그아웃은 중립적인 확인 문구와 ‘계속 이용하기’를 제공한다. 처리 중 버튼/배경/Android 닫기를 잠그고 기존 공통 로그아웃 흐름을 사용한다.
- 탈퇴는 읽기 쉬운 세 가지 안내 → 확인 체크 → 최종 확인으로 진행한다. 저장 실패 시 계정을 유지하고 재시도할 수 있다. 탈퇴 성공 이후 로그아웃 처리가 끝날 때까지 처리 중 상태를 유지한다. 이전 계정의 확인창/지연 응답이 새 계정을 탈퇴시키거나 로그아웃시키지 않도록 보호한다.
- 편집창은 키보드를 고려하고, 확인창은 고정 214/260px 높이를 제거했다. 내용에 맞춰 표시하고 화면 공간이 부족하면 창 안에서 스크롤한다. 버튼은 최소 48pt 이상, 큰 글자에서는 확인창 버튼을 세로 배치한다.
- 신규 API가 필요한 보안 기능에는 임시 토글이나 동작하지 않는 버튼을 추가하지 않았다. 네이티브 의존성/설정을 추가하지 않아 prebuild/CocoaPods 재설치가 필요하지 않다.

## 현재 API와 확인된 서버 동작

스냅샷 `.claude/artifacts/backend-schema.json`, `analysis-report.md`를 먼저 읽고 관련 소스만 재확인했다.

| 기능 | 현재 계약 | 이번 처리 |
|---|---|---|
| 계정 정보 | `GET /my-page/account` → `{name}` | 기존 조회 유지 |
| 로그인 이메일 | `GET /my-page` → `name, email, profileImageUrl` | 기존 사용자별 프로필 캐시 재사용 |
| 닉네임 변경 | `POST /my-page/account` → `{nickname}`, 성공 result는 null | 기존 API 유지; 기본/상세/계정 이름 캐시 동기화 |
| 현재 세션 로그아웃 | `POST /auth/logout`, 푸시 기기 해제 | 기존 `performLogout` 공통 흐름 유지 |
| 회원 탈퇴 | `DELETE /my-page` | 성공에만 로그아웃; 실패 시 재시도 |
| 비밀번호 찾기 | `/auth/password-reset/send-code`, `/verify-code`, `/reset` | 로그인 전용 기존 화면 유지. 로그인 중 계정 변경 화면으로 재사용하지 않음 |

확인한 현재 서버에는 기존 스냅샷 조사 후 추가된 `WithdrawnAccountCleanupScheduler`, `WithdrawnAccountCleanupService`가 있다. `User.deactivate()`는 즉시 INACTIVE 전환·refreshToken 초기화, `AuthService.login()`은 30일 미만의 정상 인증 시 재활성화한다. 청소 서비스는 30일이 경과한 계정을 찾아 `User.anonymize()`로 이름·이메일 등 계정 정보를 비식별 처리하고 푸시 기기를 삭제한다. 따라서 RN은 ‘30일 이내 로그인하면 복구 가능’이라고 안내한다. 기간 경과 후 처리는 스케줄에 따라 실행되므로 정확히 30일 되는 순간 모든 파일이 지워진다고 안내하지 않는다.

확인한 청소 코드는 S3 원본/직업 서류/AI 학습 파일의 물리 삭제까지 보장하지 않는다. 이번 UI의 ‘모든 데이터 영구 삭제’ 문구를 제거했다. 실제 배포에서 스케줄러가 활성화되어 있는지와 파일 보관/삭제 정책은 서버·운영 확인이 필요하다.

## 백엔드 요청 — 우선순위 및 계약 제안

아래 필드/엔드포인트는 현재 API에 있다는 뜻이 아니라 **추가 요청**이다. 운영자에게 자동 발송하지 않았으며 전달용 문서로 작성했다.

| 우선순위 | 요청 | 용도 |
|---|---|---|
| 1 | `GET /my-page/account` 확장: 기존 `name` 유지 + `email`, `emailVerified`, `authProviders`, `canChangePassword` | 계정 정보를 한 번에 조회하고 실제 지원하는 보안 기능만 표시. 현재 로그인 방식은 RN에서 임의로 EMAIL이라고 추측하지 않음 |
| 1 | `PATCH /my-page/account/password` | 로그인한 본인의 비밀번호 변경. 기존 비밀번호 확인 후 새 비밀번호/확인 값 검증 |
| 1 | `GET /my-page/withdrawal-info` | 서버 정본의 `recoveryPeriodDays`, `policyVersion`, 계정·서류·AI 데이터의 보관/삭제 안내, 잔여 시간/구매 처리 안내 |
| 2 | 본인 이메일 변경: 코드 발송 → 코드 검증 및 적용 | 새 이메일 소유 확인과 중복 검사 후 변경. 비밀번호 재확인 또는 재인증 토큰 필요 |
| 2 | 로그인 세션 목록·선택 로그아웃·다른 기기 모두 로그아웃 | 실제 인증 세션의 기기 이름·최근 사용 시각·현재 기기 여부 확인 및 해제 |

### 기존 계정 조회의 호환성

- `{name}`를 유지하며 신규 필드를 추가한다. 서버 지원 전/알 수 없는 `emailVerified` 등을 RN이 true 또는 false로 추측하지 않도록 nullable/지원 기능 목록을 명시한다.
- `authProviders`는 실제 연결 정보만 반환한다. 단순 로그인 UUID나 푸시 기기 목록으로 소셜 연결 상태를 추측하지 않는다.
- 변경 지원 여부는 서버가 판정한다. 소셜 전용 계정에 비밀번호 변경을 표시하지 않도록 `canChangePassword` 또는 `capabilities`를 제공한다.
- 로그인 이메일을 account API에 추가하면 RN의 별도 `/my-page` 조회는 제거하고 기존 프로필 캐시는 유지할 수 있다. 지금은 없는 필드를 가정하지 않고 기존 API를 활용한다.

### 비밀번호 변경

예시 요청: `{currentPassword, newPassword, newPasswordConfirm}`. 로그인한 본인 UUID는 인증 정보로 판정하고 요청 body의 다른 사용자 ID를 받지 않는다.

- 현재 비밀번호 불일치, 새 비밀번호 형식 불일치, 확인 불일치, 변경 제한을 안정적인 에러 코드로 구분한다. 비밀번호는 로그에 기록하지 않는다.
- 가입·비밀번호 찾기와 같은 비밀번호 검증 정책을 재사용한다. 현재 RN 닉네임의 2~10자 규칙도 가입/수정 DTO에서 같은 정책으로 검증해 API 호출만으로 우회되지 않게 한다.
- 변경 후 재로그인 여부/다른 세션 처리 규칙을 명시한다. 권장 응답: `reauthenticationRequired: true`와 세션 폐기 범위를 계약으로 확정. RN은 성공 후 로컬 상태를 정리하고 로그인으로 안내한다.
- 현재 `User.updatePassword()`는 refreshToken을 지운다. 이것이 이미 발급된 accessToken의 즉시 무효화를 보장하지는 않으므로 tokenVersion/세션 검증 등 서버 정책을 함께 확인한다. 현재 비밀번호 찾기의 HTTP 세션 인증을 로그인 중 계정 변경에 그대로 재사용하지 않는다.

### 이메일 변경

권장 예시: `POST /my-page/account/email/send-code` → `POST /my-page/account/email/confirm`. 인증 절차는 재인증된 사용자·대상 이메일·만료 시각·요청 ID에 묶는다. 재전송 횟수/검증 횟수 제한과 중복 이메일 검사는 서버에서 수행한다. 확인 API 성공 시 이메일·인증 상태를 함께 반환하고 이전 이메일에 변경 사실을 알리는 정책을 정한다. 이메일 변경 시 인증 세션 유지/폐기 여부도 비밀번호 변경과 일관되게 정한다.

### 로그인 기기 관리

현재 User에는 하나의 refreshToken을 보관하므로 다중 기기 인증 세션을 먼저 모델링해야 한다. `/push/devices`는 알림 등록 정보이며 로그인 세션 목록으로 사용할 수 없다.

예시: `GET /auth/sessions`, `DELETE /auth/sessions/{sessionId}`, `DELETE /auth/sessions/others`. 응답은 `{sessionId, deviceName, platform, lastActiveAt, isCurrent}`. 서버는 본인 세션만 열람/해제하게 하고, 현재 세션 해제는 RN에서도 즉시 로그아웃시킨다. refreshToken/accessToken 무효화와 해당 설치의 푸시 등록 해제를 일관되게 처리한다.

### 탈퇴 안내와 파일 삭제

- 정책 조회에 고객에게 실제 안내할 계정 복구, 데이터 보관, 구매/잔여 시간 처리 내용을 반환한다. RN이 환불 가능 여부나 S3 삭제 시점을 만들어 안내하지 않는다.
- 기존 `DELETE /my-page`를 깨뜨리지 않고 성공 응답에 `withdrawnAt`, `recoverableUntil`, `status`를 추가하는 확장을 권장한다. 날짜는 timezone이 명확한 ISO8601 형식으로 반환한다.
- DB 비식별 처리와 S3/AI/외부 음성 모델 정리는 분리된 작업으로 관리한다. 실패 재시도·처리 이력을 남기고, 탈퇴 뒤 늦게 완료되는 학습 작업이 계정을 다시 활성화하거나 삭제 대상 파일을 재생성하지 않게 한다.
- 폐기된 계정의 기존 accessToken, 공개 추천·대화·푸시·학습 결과 반영을 차단하는 규칙도 서버에서 확인한다.

## 검증과 실기기 확인

- 전체 Jest 63개 묶음·364개 테스트 통과. 계정 화면의 새 테스트 8개와 기존 캐시/저장 테스트를 포함한다. 기존 Sentry 타이머 때문에 최종 전체 실행에는 `--forceExit`를 사용했다.
- 변경한 계정 파일의 ESLint·TypeScript 오류 없음. 프로젝트의 기존 타입 오류는 유지했다. iOS/Android 프로덕션 JS·Hermes 번들 생성도 통과했다.
- 닉네임 읽기 실패 복구, 입력 중 재조회, 저장 실패 후 재입력 없는 재시도, 형식 검증, 계정 교체 방어를 테스트했다.
- 실제 기존 조회/저장 훅을 사용한 RN 화면 테스트로 이메일 표시·미리보기·테마·고객센터 연결을 확인했다.
- 로그아웃 취소·연속 탭, 탈퇴 동의·실패 후 재시도·로그아웃 완료 대기, 이전 계정의 탈퇴 확인/지연 응답을 검증했다.
- 실기기 확인 필요: 작은 화면/가로 방향/큰 글자에서 줄바꿈, 닉네임 키보드와 저장·취소 접근, 느린 네트워크에서 연속 탭, 확인창 닫기와 Android 뒤로가기, 탈퇴 복구 기간과 실제 배포 서버 데이터.

## 후속 디자인 조정

닉네임 옆에 ‘변경’ 버튼을 배치하고 접근성 이름은 ‘닉네임 변경’으로 유지했다. 좁은 화면과 큰 글자에서는 자연스럽게 세로 배치한다. 내 프로필 미리보기에는 카드 배경과 테두리를 적용하고 카드 전체를 누를 수 있게 했다. 새로운 서버 API는 필요하지 않다.
