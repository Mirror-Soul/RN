# 알림 설정 UX 및 백엔드 API 요청

## 이번 RN 구현

- 알림 화면을 **대화와 통화 / 대화 시간 안내 / 기기 알림 확인**으로 나눴다.
- ‘알림이 오지 않나요?’를 18pt 제목으로 분리하고 설명을 줄바꿈했다. 기기 권한을 조회해 일반 허용·조용한 알림 허용·꺼짐을 구분하고 기기 설정을 연다. 화면 진입·복귀에는 권한 요청 팝업을 띄우지 않는다.
- 스위치는 OS 표준 디자인과 **켜짐 / 꺼짐 / 저장 중 / 확인 필요** 문구를 함께 사용한다. 읽기 전 값을 꺼짐으로 확정하지 않는다. 48pt 이상의 터치 영역, 스크린 리더 상태 안내, 작은 화면·큰 글자에서 제목/스위치의 세로 배치를 제공한다.
- 메시지 알림 항목을 누르면 대화방별 알림 관리 시트를 연다. `GET /chat/rooms`의 `notificationEnabled`를 활용해 목록을 한 번 조회한다. 각 행을 표시하려고 설정 API를 추가 호출하지 않는다. 대화방 수가 많아도 FlatList로 필요한 행만 표시한다.
- 변경은 기존 `PATCH /chat/rooms/{room-id}/notification`, body `{ "enabled": false }`를 사용한다. 대화방 안의 옵션도 같은 저장/캐시 갱신 로직과 스위치를 쓴다.
- 빠른 연속 저장을 막고, 저장 성공 후 확정값을 반영한다. 실패하면 이전 값을 유지하고 관리 시트 안에도 오류를 표시해 재시도할 수 있게 한다. 알림 관리 목록·대화방 옵션 캐시는 사용자 UUID로 분리하며, 이전 계정의 늦은 응답이나 버튼 콜백을 무시한다. 저장 전 시작된 조회가 이후 확정값을 덮어쓰지 않도록 취소한다.
- Android는 OS 설정에서 새로 허용한 뒤 앱으로 복귀하면 기존 푸시 토큰 등록 흐름을 재실행한다. 복귀 때 권한을 다시 요청하지 않고, 동일 세션·동일 토큰의 불필요한 재등록을 생략한다.
- 백엔드·AI·인프라 소스는 수정하지 않았다. 새 서버 필드가 필요한 전체 메시지/완료 알림에는 아직 동작하는 것처럼 보이는 토글을 만들지 않았다.

## 현재 서버에서 이미 제공하는 기능

먼저 API 스냅샷을 확인하고 변경 가능성이 있는 채팅 관련 소스만 재확인했다.

| 기능 | 현재 API/소스 | 판단 |
|---|---|---|
| 시간 부족·부재중 통화 선호도 | `GET/PATCH /my-page/alarm` | 기존 두 필드로 조회/저장 연결. 설정 조회/저장만 구현. `CallService`/`PushNotificationService`에 실제 통화·시간 부족 발송 이벤트는 없음 |
| 내 트윈 통화 알림 | 현재 설정 필드·발송 이벤트 없음 | RN에 ‘준비 중’ 안내 추가. 동작하는 토글은 서버 계약·발송 기능 완성 후 연결 |
| 대화방별 메시지 알림 | `GET /chat/rooms`, `GET/PATCH /chat/rooms/{room-id}/notification` | API 이미 존재. 새 API 없이 RN 관리 UI 제공 |
| 메시지 발송 대상 필터 | `PushNotificationService.sendChatMessage`, `ChatRoomMemberRepository.findPushRecipientUuids` | `notificationEnabled=true`, 활성 멤버, 발신자 제외, 차단 관계 제외를 서버에서 적용 |
| 메시지 푸시 내용 | `PushNotificationService.sendBatch` | 발신자 이름과 ‘새 메시지가 도착했습니다.’ 표시. 실제 메시지 본문은 미포함 |
| 푸시 기기 등록 | `PUT /push/devices` | 기존 API 유지. RN에서는 OS 권한 변경 후 등록 복구 보완 |
| iOS 실제 푸시 전달 | RN `usePushNotificationSetup` | 현재 APNs 준비 전이라는 기존 Android 전용 등록 가드가 남아 있음. OS 허용 표시만으로 실제 푸시가 전달된다는 뜻은 아님 |

## 백엔드 요청 — 추가 필드 제안

아래는 현재 API에 존재하는 필드가 아니라 **추가 요청**이다. 우선 전체 메시지 알림과 만남 요청 알림부터 정하고, 완료 알림은 실제 처리 결과 이벤트가 준비된 다음 제공하는 것을 권장한다.

기존 `GET/PATCH /my-page/alarm`을 확장해 설정의 정본을 한 곳에서 관리한다. 대화방별 API는 그대로 유지한다.

| 우선순위 | 추가 필드 | 용도 / 발송 조건 | 권장 초기값 |
|---|---|---|---|
| 1 | `chatMessageNotificationEnabled: boolean` | 모든 대화방 메시지 푸시의 상위 수신 설정. 방별 설정과 함께 검사 | `true` — 기존 방별 알림 동작 유지 |
| 1 | `meetingRequestNotificationEnabled: boolean` | 새 만남 요청과 본인 요청의 수락 등 실제 대응이 필요한 소식 | `true` |
| 1 | `twinCallNotificationEnabled: boolean` | 다른 회원이 내 트윈과 실제 대화를 마쳐 History에 표시될 때 소유자에게 발송. 자기 트윈 통화·연결 실패·취소 제외 | `true` |
| 2 | `twinReadyNotificationEnabled: boolean` | 가입 트윈 준비 또는 음성/얼굴 업데이트 완료 시 결과 안내 | `true` |
| 2 | `jobVerificationNotificationEnabled: boolean` | 직업 인증 승인·반려·보완 요청 안내. 심사 상태/API 구현 후 제공 | `true` |
| 선택 | `messagePreviewEnabled: boolean` | 잠금 화면에 실제 메시지 본문을 표시할지 선택. 표시하지 않으면 현재 일반 안내 유지 | `false` |

초기값은 제안이며 제품 정책을 확정한 뒤 적용한다. 혜택/이벤트 알림은 서비스 소식과 분리해서 별도 수신 동의·발송 체계가 준비될 때 추가한다. 방해 금지 시간·알림 소리는 우선 기기의 집중 모드/알림 채널 설정을 활용하고 중복 설정 화면을 만들지 않는다.

## 계약 및 발송 규칙

1. **호환성:** 기존 `missedCallNotificationEnabled`, `lowTimeNotificationEnabled` 이름과 의미는 유지한다. 새 필드를 필수 요청값으로 만들어 기존 RN의 PATCH를 깨뜨리지 않는다. PATCH는 전송한 필드만 수정하고, 빠진 필드는 유지한다. `false`를 누락처럼 취급하지 않는다.
2. **조회:** 지원되는 필드는 저장된 확정값을 반환한다. 단계적으로 출시한다면 `supportedNotificationTypes` 같은 지원 목록을 함께 반환해 RN이 아직 지원하지 않는 설정을 숨길 수 있게 한다. RN에서 응답에 없는 필드를 임의로 true로 표시하지 않는다.
3. **메시지 수신:** `전체 메시지 설정 && 대화방 설정 && 활성 멤버 && 차단 관계 아님 && 등록된 기기 활성`일 때 발송한다. 전체를 꺼도 각 방의 선호도를 변경하지 않는다. 다시 켜면 이전 방별 설정을 그대로 적용한다. 기기 OS 권한은 별도로 전달을 제어한다.
4. **개인정보:** `messagePreviewEnabled=false`일 때 본문을 푸시 notification/data에 싣지 않는다. 현재의 일반 안내 문구를 유지한다. true일 때도 잠금 화면에 표시할 길이/내용 정책을 별도로 정한다.
5. **완료 알림:** AI/심사 완료 이벤트를 backend에서 수신해 사용자 설정을 검사하고 발송한다. AI에서 직접 기기 푸시를 보내지 않는다. AI 모델 완료와 미리듣기 파일 준비는 다른 상태일 수 있으므로 실제 완료 조건을 명시한다.
6. **중복 방지:** 사용자·이벤트 종류·작업/제출/메시지 ID로 중복 발송을 방지한다. 작업 재시도나 SQS 재전달 때문에 같은 완료 알림을 반복하지 않는다. 오래된 작업의 지연 완료가 최신 결과 안내를 덮어쓰지 않게 한다.
7. **소리/기기:** 알림 종류가 늘면 Android 메시지·통화·서비스 안내 채널을 구분하고 backend channelId와 RN 생성 채널을 일치시킨다. iOS APNs 자격 증명·앱 서명·기기 토큰 등록을 함께 검수한 후 RN의 기존 Android 가드를 해제한다. 이번 작업에서 네이티브 설정은 변경하지 않았다.
8. **OS 차단:** 설정 저장 성공과 푸시 전달 성공은 구분한다. 기기에서 차단된 알림을 앱 내 설정으로 강제로 허용하지 않는다. 이미 발송 큐/기기에 전달된 알림까지 새 토글로 회수할 수 있다고 보장하지 않는다.

## 통화 알림 추가 요청

- 현재 `missedCallNotificationEnabled`는 조회/저장에만 쓰인다. `CallService`와 푸시 발송 구현을 확인했으며, 실제 발송은 채팅 메시지만 존재한다. 부재중 통화의 제품 의미(누가 어떤 전화를 받지 못했는지)와 발생 조건을 먼저 정의해야 한다. 자동으로 응답하는 AI 트윈 연결 실패를 상대방의 부재중 통화로 처리하지 않는다.
- 내 트윈 통화 알림은 backend `endCall`에서 `COMPLETED` 확정 및 트랜잭션 커밋 후 **트윈 소유자**에게 보낸다. 발신자 자신에게 보내지 않고, 자기 트윈과의 통화도 제외한다. History와 동일한 공개/차단/계정 상태 규칙을 적용한다. AI 분석 완료까지 기다릴 필요는 없다. 분석 결과가 필요하다면 별도 완료 이벤트로 정의한다.
- `twinCallNotificationEnabled` 조회·저장과 실제 발송을 함께 출시하고, `TWIN_CALL_COMPLETED` payload에 `eventId`, `callId`를 포함한다. History 해당 통화로 이동할 수 있도록 안정적인 이동 계약을 제공한다. 같은 `callId`의 반복 종료·재시도는 중복 발송하지 않는다. 메시지 본문·녹음·민감한 대화 내용은 알림에 싣지 않는다.
- RN은 새로운 설정을 임의로 로컬 저장하지 않았다. 현재 화면에 준비 중 안내만 보이며, 서버가 계약을 제공하면 같은 알림 설정 쿼리/저장 흐름에 연결한다.

## 간격 및 저장 중 표시 개선

- 섹션 간격은 20→12pt, 제목과 카드 간격은 8→4pt, 항목의 세로 패딩은 16→8pt로 조정했다. 제목과 설명을 하나의 묶음으로 스위치 옆에 배치해 제목 위의 빈 공간을 줄였다. 메시지 관리의 중복 안내를 줄이고, 기기 권한 안내는 한 설명 영역에 모았다.
- 스위치 터치 영역은 최소 48pt를 유지한다. 저장 중 다른 항목은 입력만 막고 색·값·투명도를 유지한다. 저장 중인 항목에만 ‘저장 중’을 표시한다. 이 규칙은 대화방별 알림에도 적용된다.
- 대화방 관리 시트는 고정 85% 높이 대신 내용에 따라 커지고, 최대 높이에서는 목록만 스크롤한다. 상단 안전 영역을 넘지 않게 제한한다. 작은 화면·큰 글자에서는 제목/스위치를 세로 배치하며 텍스트 높이를 고정하거나 말줄임하지 않는다.

## 검수 항목

- 방별 변경: 켜기/끄기 → 대화방 옵션과 목록 값 일치 → 다른 방 설정 보존 → 앱 재실행.
- 저장 실패/읽기 실패/빠른 반복 탭/저장 중 재조회/로그아웃·계정 교체.
- 전체 메시지 끄기/다시 켜기에서 기존 방별 값 유지; 방에서 껐으면 전체가 켜져 있어도 미발송.
- 차단·탈퇴·나간 방·기기 등록 해제에서 미발송.
- OS 거부 → 설정 허용 → 앱 복귀 → 토큰 등록 복구, 권한 팝업 반복 없음.
- iOS 실제 APNs 전달, Android 채널 비활성/집중 모드, 실제 알림 탭 후 올바른 대화방 이동.
- 작은 화면·큰 글자·긴 상대 이름에서 항목 줄바꿈, 시트 스크롤 및 닫기 버튼 접근.

UI 조정은 네이티브 의존성을 추가하지 않는다. 프리빌드/CocoaPods 재설치는 필요하지 않다. 새 알림 종류/채널의 구현과 배포는 서버 계약 확정 후 별도로 진행한다.

## RN 검증

- 전체 Jest: 63개 묶음·364개 테스트 통과(후속 계정 UX 테스트 포함). 대화방 시트에서 실제 조회/저장 훅으로 변경·실패 후 재시도를 검증했다. 다른 스위치의 표시 유지·미지원 트윈 알림 안내, 빠른 반복 저장·계정 변경·저장 중 재조회 경합, 기기 권한 확인·설정 열기 실패, Android 권한 변경 후 등록도 검증했다.
- 이번 알림 변경 파일의 ESLint·TypeScript 오류 없음. 저장소의 기존 타입 오류는 별도로 남아 있다.
- iOS/Android 프로덕션 JS·Hermes 번들 생성 통과. 다양한 실기기의 실제 레이아웃·스크린 리더·푸시 전달은 직접 검증하지 않았다.
